# v0.3.5 Engineering Audit — 2026-10-15

Scope: MCP HTTP dispatch, trace/diagnostic logging, Admin controls, unprivileged durable jobs/PTY, and optional Desktop Commander process interaction. Review includes static inspection, actual PTY sessions, runtime tests, loopback benchmarks, fresh installation and isolated upgrade/rollback simulations.

## Fixed

1. **O(N) Trace lookup**: Exact Trace IDs previously parsed every retained JSON record. Now only directory names are enumerated and the single matching file is loaded.
2. **Unbounded PTY input deduplication**: Long-lived sessions retained all input request-id hashes. Limited to 4,096 IDs; exhaustion rejects fresh IDs rather than evicting old IDs and causing unsafe retries.
3. **PTY read ergonomics**: Optional wait_for_prompt avoids sending stdin twice due to asynchronous output, and tail_lines gives bounded recent output without changing the byte cursor.
4. **Missing performance visibility**: Opt-in metadata-only telemetry captures HTTP read/JSON parse/dispatch, tool milestones, total duration, output sizes and logical errors. Commands, arguments, outputs, tokens, URLs and exception text are excluded.
5. **Diagnostic retention**: Rotated JSONL with per-file size caps, bounded write queue and observable storage errors.

## Remaining constraints

- Historical job state metadata still includes argv. Secrets placed in shell command-line arguments can persist in protected state files, independently of the new debug mode. Removing those fields requires a separate review of the existing job_read include_command contract.
- util-linux script PTY currently has no window resize API. Prompt detection is heuristic; always verify status/exit codes.
- Jobs can survive HTTP gateway restarts, not host reboots.
- Separate Linux users/systemd permissions do not constitute a full hostile-code sandbox. No Bubblewrap or handle-relative secure writes added.
- Loopback benchmarks do not measure end-to-end ChatGPT network latency. Repeat before making causal performance claims.

## v0.3.6 follow-up: sensitive raw payload capture

A full request/response journal is now available as a second explicit Admin opt-in, separate from the metadata performance log. Fresh Admin password confirmation is required for enabling, reading or downloading capture content. The generic settings route cannot enable it. HTTP auth headers and Admin requests are never saved. Limits, rotation and clear are tested.

This is intentional high-sensitivity logging: JSON-RPC bodies and tool responses **can** contain tokens, secrets or files. Enabling it temporarily trades confidentiality and storage/I/O for reproducible debugging. With debugging off, the HTTP handler performs only a cheap branch and no extra clocks, listeners, copies, formatting or log writes.

Remaining items: optional automatic capture expiry and selective field redaction could further reduce operational risk, but are not implemented in this release. Individual tool output truncation is independent of the capture body-size limit.

The sensitive capture queue is also bounded to 32 MiB of clipped message previews to avoid keeping unlimited large request/response bodies in memory while the disk is congested. If exceeded, capture records are dropped and surfaced as a diagnostic counter.
